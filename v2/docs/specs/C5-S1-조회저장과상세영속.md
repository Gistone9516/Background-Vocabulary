## 1. 왜 열거 교체가 아니라 제거인가

사용자 결정은 "태그 3종을 폐기하고 조회/저장으로 일원화"였다. 이를 `TAGS`의 값만 바꾸는 것으로 구현하면 안 된다.

**조회와 저장은 동시에 참일 수 있다.** 상세를 펼치고 담은 어휘는 둘 다이고, 펼치지 않고 담을 수도(카드에서 바로 담기), 펼치고 안 담을 수도 있다. 단일 `tag` 컬럼은 이 상태를 표현하지 못한다. 값만 갈아끼우면 첫 번째 경우에서 둘 중 하나가 조용히 소실된다.

그리고 두 사실을 담을 자리가 각각 따로 있다.

| 사실 | 어디에 | 상태 |
|---|---|---|
| 저장 | `assets` 행의 존재 (`user_id`, `session_id`, `term_norm`) | **이미 있다.** FR-601·FR-706이 이미 쓴다 |
| 조회 | `details` 행의 존재 | 신설 |

**조회 기록과 상세 본문 저장은 같은 것이다.** 본문이 저장돼 있다는 사실 자체가 그 어휘를 펼쳤다는 기록이므로, 별도 플래그를 두면 그 순간 한 사실에 두 출처가 생긴다.

따라서 이 슬라이스는 축을 바꾸는 것이 아니라 **`Tag` 축을 걷어내고 `details`를 세우는 것**이다.

### 왜 태그가 제거 가능한가 (실측)

`recommend.ts`가 LLM에게 `Always set tag to "몰라"`를 지시하므로 `Term.tag`는 항상 `"몰라"`다. `summarize.ts`는 그 태그로 `known_terms`/`unknown_terms`를 가르므로 `known_terms`는 구조적으로 항상 빈 배열이고, `primer_known` 문구는 화면에 뜬 적이 없다. `TAGS` 상수를 순회하는 UI는 저장소에 0곳이다. 태그 축은 작동한 적이 없으므로 제거는 기능 손실이 아니다.

FR-502("알아 → 추천 제외")의 실질은 FR-706("프로젝트의 담은 어휘는 신규 추천에서 중복 제외")이 이미 수행하며, 저장 축과 그대로 맞물린다.

## 2. 계약 변경

### 2-1. 제거

`Tag` · `TAGS` · `Term.tag` · `KnowledgeState` · `KnowledgeRepository` · `PUT /knowledge` · `GET /knowledge` · `knowledge` 테이블.

### 2-2. 신설 — `DetailRec`

```
DetailRec {
  user_id     TEXT     소유자. 캐시는 사용자 간 공유하지 않는다(E-4)
  session_id  TEXT     어느 세션에서 펼쳤는가. S2 패널의 1스코프
  term_norm   TEXT     표시·조회용. 캐시 키가 아니다(E-3)
  input_key   TEXT     Prompt5In + 프롬프트 버전에서 조립한 키. 캐시 판정은 이것만 본다
  body        JSONB    Prompt5Out 전체
  created_at  BIGINT
  PRIMARY KEY(user_id, input_key)
}
```

### 2-3. `PrimerDoc` 어휘 분리 폐기

`known_terms: string[]` · `unknown_terms: string[]` → `terms: string[]` 단일 배열. 태그가 사라지면 서버가 가를 근거가 없다. 조회/저장 분리 표시는 클라가 `assets`·`details`로 하며(S2), 서버가 다시 판정하면 같은 구분에 두 출처가 생긴다.

## 3. `/detail` 회로

`/detail`은 현재 스트리밍이 아니라 완결 JSON을 돌려준다(`return c.json(await pipeline.detail(...))`). 따라서 저장은 서버에서 원자적으로 일어나고 **클라이언트 변경이 없다.**

```
POST /detail
  ├ input_key 조립 → details 조회
  ├ 히트 → body 그대로 반환. LLM 0회, 한도 차감 0 (E-5)
  └ 미스 → 게이팅 통과 → pipeline.detail → 저장 → 반환
```

클라의 `DetailCache`(메모리)는 그대로 둔다. 서버 캐시와 두 벌이 아니라 계층이 다르다 — 메모리는 같은 화면에서 접었다 펴는 왕복을 없애고, 서버는 세션을 나갔다 온 재생성을 없앤다. 판정 권위는 언제나 서버다.

## 4. 동작 규칙

| # | 규칙 | 근거 |
|---|---|---|
| E-1 | 조회와 저장을 단일 열거로 표현하지 않는다. 저장 = `assets` 행, 조회 = `details` 행 | 두 사실이 동시에 참일 수 있다(§1) |
| E-2 | 조회 여부를 나타내는 별도 필드·플래그를 두지 않는다. `details` 행의 존재가 곧 조회다 | 한 사실에 두 출처를 만들지 않는다 |
| E-3 | 캐시 키는 `Prompt5In` 전 필드(`term`·`kind`·`area`·`job_type`·`domain`·`topic`·`locale`·`connection_hint?`)에서 **고정 순서로** 조립한다. `term_norm`만으로 키를 만들지 않는다 | `Prompt5Out.whymine`은 "왜 나에게 중요"라 세션 맥락에 의존한다. 어휘 단위로 캐시하면 다른 세션의 내 맥락이 나오고, 사용자는 틀렸음을 알아챌 수 없다 |
| E-4 | 캐시는 `user_id`에 귀속된다. 사용자 간 공유를 구현하지 않는다 | 같은 근거. `whymine`은 개인 맥락이다 |
| E-5 | 캐시 히트는 한도를 차감하지 않는다. 그러므로 캐시 조회가 게이팅보다 앞선다 | 이미 지불한 생성을 다시 청구하지 않는다. 미들웨어가 라우트보다 먼저 도는 현 구조에서 이것은 배선 순서 요구다 |
| E-6 | 저장은 성공 응답에 대해서만 한다. 실패·중단은 남기지 않는다 | 반쪽 본문이 캐시되면 다음 열람이 잘린 내용을 정본으로 받는다 |
| E-7 | 캐시 키에 프롬프트 버전 상수를 포함한다 | 넣지 않으면 상세 프롬프트를 개편해도 옛 본문이 영구히 나온다. 개편이 반영되지 않는데 화면은 정상으로 보인다 |
| E-8 | `details.body`는 목록 응답에서 제외한다 | 대형 JSONB. Data API 1MB 상한. `SessionSummary`가 `narrow`·`generated`·`primer`를 뺀 것과 같은 규칙 |
| E-9 | 클라 `DetailCache`는 유지한다. 서버 캐시와 계층이 다르다 | §3. 두 벌 금지는 같은 층위의 두 판정을 막는 규칙이지 계층 캐시를 막는 규칙이 아니다 |
| E-10 | 베이스라인에서 지우는 문구는 `/recommend`·`/summarize`에 속한 것만이다. 다른 프롬프트의 문구가 함께 줄면 사고다 | C3-S4b §2 선례의 조건을 그대로 승계 |
| E-11 | `PUT /knowledge` 제거와 함께 `Repositories`에서 `knowledge`를 뺀다. 포트만 남기지 않는다 | 소비자 없는 export는 작동하는 동작으로 오인된다(코드규약·VF-17) |
| E-12 | 마이그레이션은 `knowledge`를 `DROP TABLE IF EXISTS`로 내린다. 컬럼만 놔두지 않는다 | 값 도메인을 검사하는 게이트가 없어(TEXT·CHECK 없음) 남은 테이블은 조용히 옛 값을 계속 받는다 |

## 8. 검증

`e2e-detail.mjs`는 "캐시는 카드 id 기준·클라 메모리"를 전제로 쓰였으므로 문자열 치환이 아니라 재작성한다. 서버 쪽은 `e2e-pg.mjs`가 본다.

| 케이스 | 기대 |
|---|---|
| 같은 세션에서 같은 어휘 재열람 | LLM 호출 0회, 본문 동일 (E-3) |
| `topic`만 다른 요청 | 캐시 미스, 새 생성 (E-3) |
| 다른 `user_id`의 같은 `input_key` | 캐시 미스 (E-4) |
| 캐시 히트 시 한도 | 차감 0 (E-5) |
| 생성 실패 후 재요청 | 저장된 것 없음, 다시 생성 (E-6) |
| 프롬프트 버전 상수 변경 | 전건 캐시 미스 (E-7) |
| `details` 목록 조회 | `body` 미포함 (E-8) |
| `PUT /knowledge` | 404 (E-11) |
| 마이그레이션 후 | `knowledge` 테이블 부재 (E-12) |
| `prompt-parity` | 통과, `/recommend`·`/summarize` 외 문구 수 불변 (E-10) |

## 9. 열린 항목

- **`/detail` 스트리밍 미구현.** FR-401은 "펼친 순간부터 스트리밍으로 채우고"를 요구하는데 현 구현은 완결 JSON이다. 이 슬라이스는 캐시 요구만 충족하고 스트리밍은 손대지 않는다 — 범위를 넘고, 오히려 스트리밍이 없어서 서버 저장이 원자적이 된다. 별도 판단 필요.
- **조회 목록 조회 API는 S2에서.** 소비자(우측 패널)가 같은 커밋에 없으면 inert export가 된다(E-11과 같은 근거).
- **기존 JSONB에 박제된 `tag`.** `sessions.generated`·`assets.term`에 과거 값이 남을 수 있다. 미배포이므로 백필하지 않되, 읽는 쪽이 `tag`를 참조하지 않게 되므로 무해하다.
