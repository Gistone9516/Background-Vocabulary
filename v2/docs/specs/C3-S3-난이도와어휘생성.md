# C3 S3 스펙 — 난이도 선택과 어휘 생성 (SoT §1·§3-1·§5에서 파생)

> 상위 = [C3-웹랜딩.md](C3-웹랜딩.md). 앞 = [C3-S2](C3-S2-진입과좁히기.md).
> v1 코드는 **동작 명세로만** 쓴다. 구조는 계승하지 않는다(코드규약 §6~§9).

## 0. 범위

- **포함**: `/preview`(난이도 대표 어휘) · difficulty 화면 · SSE 클라이언트 · `/recommend` 스트리밍 · terms 카드 목록 · 취소와 watchdog · 누적 상한.
- **제외**: 담기 영속(S4) · 세션 서버 저장(S5) · 광고 슬롯(C5).

### 0-1. 상위 스펙에서 벗어나는 결정 2건 (사유 명시, 검토 요청)

| 항목 | C3 스펙 | 제안 | 사유 |
|---|---|---|---|
| **relate(연결 턴)** | S3 | **S5로 이월** | `RelateIn.kept`가 **프로젝트에 이미 담은 어휘**를 요구한다. 담기는 S4, 프로젝트는 S5다. S3에서는 `kept`가 항상 빈 배열이라 서버가 `relevant:false`를 돌려주고 이 턴은 **매번 건너뛴다.** 한 번도 발동할 수 없는 코드를 넣고 게이트를 통과시키는 셈이다. S2에서 SSE 클라이언트를 소비처가 생기는 슬라이스로 옮긴 것과 같은 이유다 |
| **detail(카드 상세)와 그룹별 추가 생성** | S3 | **S3b로 분리** | S3만으로 "난이도를 고르면 어휘가 쌓인다"는 완결된 결과가 나오고 눈으로 검증된다. detail은 자기 게이팅(무료 열람 횟수 NFR-304)과 출처 렌더와 캐시 재사용을 따로 갖는 별개 관심사다. 한 슬라이스에 묶으면 검증 단위가 흐려진다 |

두 건 다 **승인 대상**이다. 반대하시면 S3에 그대로 포함해 진행한다.

## 2. v1 구조에서 바꾸는 것

| v1 | 문제 | v2 |
|---|---|---|
| 스트림 콜백 안에서 `sref.current`로 최신 목록을 읽어 상한을 검사 | S2에서 없앤 stale 패턴이 그대로 남아 있다 | 상한 검사는 리듀서 안에서. 콜백은 이벤트만 올린다 |
| `abortRef`, `previewAbortRef`, `watchdog` 타이머가 각각 별도 ref | 정리 지점이 흩어져 하나를 빠뜨리면 누수 | 러너 하나가 요청과 시계를 함께 소유하고 한 번에 정리 |
| `_new` 플래그를 780ms 뒤 `setTimeout`으로 되돌림 | 상태에 애니메이션 시간이 섞임. 언마운트 시 타이머 누수 | 등장 강조는 CSS 애니메이션에 맡기고 상태에서 뺀다 |
| `merge`로 목록과 로딩과 오류를 각각 갱신 | 어떤 조합이 유효한 상태인지 알 수 없음 | phase 하나로 표현. 로딩과 오류가 동시에 참일 수 없다 |
| 상한 도달을 콜백에서 `ctrl.abort()`로 처리 | 취소가 상태 전이와 분리되어 순서가 보장되지 않음 | 상한 도달도 전이. 결과로 abort 명령이 나온다 |

## 4. 계약

### 4-1. ApiPort 확장

```ts
preview(input: PreviewIn, signal?: AbortSignal): Promise<PreviewOut>;
// 서버가 SSE로 흘리는 것을 이벤트 순서 그대로 넘긴다. 취소는 signal로 전파한다.
recommendStream(input: RecommendInput, signal: AbortSignal): AsyncIterable<StreamEvent>;
```

`StreamEvent`는 `@vock/shared`의 것을 그대로 쓴다(`term` · `done` · `error{code,message}`). mock 계층도 같은 스키마를 재현하므로 클라 파서를 목으로 검증할 수 있다(SoT §5).

### 4-2. terms 상태 기계

```ts
export type TermsState =
  | { phase: "idle" }
  | { phase: "streaming"; runId: number; items: Term[]; append: boolean }
  | { phase: "settled"; items: Term[]; reason: SettleReason }
  | { phase: "failed"; items: Term[]; error: ApiError };  // 받은 것은 남긴다

export type SettleReason = "done" | "capped" | "aborted";
```

- **로딩과 오류가 동시에 참일 수 없다.** v1은 `streaming`과 `errorMsg`가 독립 필드라 둘 다 참인 상태가 표현 가능했다(코드규약 §8).
- 실패해도 이미 받은 카드는 버리지 않는다. 부분 결과가 사용자에게는 가치가 있다.

명령: `openStream` · `abort` · `armWatchdog` · `goRefusal` · `completeSession`.

### 4-3. 누적 상한

상한 검사는 리듀서 안에서 한다. `items.length >= maxTotal[tier]`이면 다음 `term` 이벤트를 받지 않고 `settled(capped)`로 가며 `abort` 명령을 낸다. **화면 코드에는 상한 숫자가 나타나지 않는다.**

## 5. 검증 (게이트 편입)

`packages/scripts/e2e-terms.mjs`를 `gate`에 추가한다. 네트워크 없이 전이만 돌린다.

| 케이스 | 기대 |
|---|---|
| term 이벤트 3건 | items 3, phase=streaming |
| done | phase=settled, reason=done, completeSession 명령 |
| 상한 도달 | phase=settled, reason=capped, abort 명령 |
| 상한 이후 term 이벤트 | items 불변 |
| error code=HIGH_RISK_REFUSED | goRefusal 명령 |
| error 일반 | phase=failed, **받은 items 보존** |
| 새 생성 시작 | 이전 items 비움, 이전 runId abort |
| 이어붙이기 시작 | items 유지, exclude에 기존 term 전달 |
| runId 불일치 이벤트 | 상태 불변, 명령 0개 |
| 감시 시계 만료 | phase=settled, reason=aborted, 로딩 해제 |
| 어떤 종료 경로든 | phase가 streaming으로 남지 않음(R-10 불변식) |

프리뷰는 `e2e-preview` 없이 terms 게이트에 캐시 키 판정만 순수 함수로 포함한다(P-2).

## 6. 함께 처리하는 것

- terms와 difficulty 화면이 쓰는 `tokens.css` 구간을 rem으로 옮긴다(S2와 같은 규칙).
- 문구는 v1 원문을 그대로 쓰고 키만 추가한다. 새로 쓰는 문구는 `[신규]`로 표시해 검토받는다.
- S2에서 만든 `saveSnapshot` 명령은 아직 저장소에 배선되지 않았다. S5에서 닫는다(아래 열린 항목).

## 7. 열린 항목

- `saveSnapshot`과 `completeSession`은 명령으로 선언만 되어 있고 저장소 구현이 없다. 기계가 "언제 저장할지"를 아는 것은 맞고 저장소는 S5에 온다. 그때까지 **명령이 발행되고 아무도 처리하지 않는 상태**임을 인지하고 있어야 한다.
- 이어붙이기(조건 재탐색)는 v1에서 pro 전용이었다. 티어 판정은 S4에서 붙으므로 S3에서는 진입점을 만들지 않는다.
