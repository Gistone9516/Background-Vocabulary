# C3 S2 스펙 — 진입과 좁히기 (SoT §1·§3-1·§4에서 파생)

> 상위 = [C3-웹랜딩.md](C3-웹랜딩.md). 이 문서는 S2 한 슬라이스의 구현 계약이다.
> v1 코드는 **동작 명세로만** 쓴다. 구조는 계승하지 않는다(사용자 지시 2026-07-28).

## 0. 범위

- **포함**: API 클라이언트(classify·next), 에러 분류, 좁히기 상태 기계, `narrow` 화면, entry에서 narrow로의 실연동, dev CORS, narrow 구간 치수 전환, `/config`에 `narrowMin` 추가.
- **제외**: terms 화면과 `/recommend`(S3), preview·relate(S3), paywall 화면(S4), 세션 서버 저장(S5).
- **패키지 경계 주의**: `narrowMin` 추가는 `shared/types/limits.ts`와 `http-app`을 건드린다. ui-shared 밖으로 나가는 유일한 변경이며, 서버 계약 변경이므로 e2e-local의 `/config` 검사도 함께 갱신한다.

### 0-1. 상위 스펙에서 벗어나는 결정 (사유 명시)

| 항목 | C3 스펙 | S2에서 | 사유 |
|---|---|---|---|
| SSE 클라이언트 | S2 범위 | **S3로 이월** | 소비처(terms)가 S3에 생긴다. 지금 만들면 아무도 호출하지 않는 inert 코드가 게이트를 통과한 채 출하된다 |
| 주간 한도 소진 UI | S4 paywall | **entry 인라인 안내** | S2에서 402가 실제로 발생한다. 화면 없이 두면 사용자가 멈춘 이유를 모른다 |

### 0-2. S2의 종료 지점

S2에는 terms 화면이 없다. 좁히기가 끝나면 **임시 확인 화면**으로 간다. 좁히기 결과(답변 이력, 남은 질문 수, 종료 사유)를 그대로 보여주는 최소 화면이며, S3에서 terms로 교체된다. 슬라이스 시각 확인을 위해 필요한 최소 산출이지 제품 화면이 아니다.

### D-9 고지 정책

| 사유 | 고지 | 성격 |
|---|---|---|
| `enough` | 함 | 긍정. 방향을 찾았다는 톤 |
| `exhausted` | 함 | 사실 전달. free면 상위 티어 안내를 덧붙일 수 있다(문구는 S4에서 확정) |
| `user_jump` | **안 함** | 사용자가 직접 누른 결과라 알릴 것이 없다 |
| `malformed` | **안 함** | 내부 오류다. 사용자에게 원인을 설명할 수 없고 불안만 준다. 조용히 진행한다 |

사유는 S2가 만들어 `NarrowCtx`에 실어 넘기고, 최종 렌더는 terms(S3)가 한다. S2에서는 임시 확인 화면(§0-2)이 그대로 노출해 검증한다.

### D-2·D-4 적용 후 종료 조건

`실답변수 = 어려워요를 제외한 답변 턴 수` 라 할 때,

1. `실답변수 >= narrowMin && out.enough`
2. `실답변수 >= narrowMax[tier]`
3. 응답 형태가 깨짐(B-5, B-7)

v1의 세 번째 조건이었던 "예산 0"은 D-4로 조건 2와 같은 식이 되어 사라진다. `실답변수 + 남은턴 = narrowMax`가 항상 성립하기 때문이다. v1의 "0답 생성 금지" 가드도 불필요해진다. 조건 2는 `narrowMax >= 1`인 한 0답에서 참이 될 수 없다.

## 4. 계약

### 4-1. ApiPort

```ts
export interface ApiPort {
  classify(input: Prompt1In, signal?: AbortSignal): Promise<Prompt1Out>;
  next(input: Prompt2In, signal?: AbortSignal): Promise<Prompt2Out>;
}
```

입출력 타입은 `@vock/shared`의 것을 그대로 쓴다. 구현 `HttpApiClient`의 주입 = `{ baseUrl; getAccessToken(): string | null; fetch?: typeof fetch }`. `fetch`를 주입 가능하게 두는 이유는 C4 Tauri가 자체 HTTP를 쓸 수 있기 때문이다.

### 4-2. ApiError

서버 실제 응답 형태를 확인해 확정했다(`http-app/src/middleware/gating.ts`). 응답 본문은 `{ error: "CODE", message: "한국어 문구" }`이며 **필드명은 `code`가 아니라 `error`다.** 스펙 초안이 `code`로 가정했던 것을 정정한다(규칙 5-2, 규칙이 틀린 경우).

| HTTP | error | 발생 지점 | ApiError |
|---|---|---|---|
| 402 | `WEEKLY_LIMIT` | gating.ts:71 | `weekly_exhausted` |
| 402 | `PRO_ONLY` | gating.ts:82 | `pro_only` |
| 402 | `DETAIL_LIMIT` | gating.ts:94 | S2 범위 밖(`/detail` 미사용). `server`로 떨어뜨리고 S3에서 분기 추가 |
| 403 | `HIGH_RISK_REFUSED` | gating.ts:61 | `high_risk` |
| 429 | `RATE_LIMITED` | gating.ts:46-47 | `rate_limited` |
| 429 | `CAPACITY` | gating.ts:48 | `rate_limited` |

```ts
export type ApiError =
  | { kind: "weekly_exhausted"; message: string }
  | { kind: "pro_only"; message: string }
  | { kind: "high_risk"; message: string }
  | { kind: "rate_limited"; message: string }
  | { kind: "network" }
  | { kind: "malformed" }
  | { kind: "server"; status: number; message: string };

export function isRetryable(e: ApiError): boolean;   // network, rate_limited, server 5xx (D-7)
```

- 분류는 `classifyError` 한 함수가 전담한다. 화면 코드에 status 숫자나 error 문자열이 나타나면 규약 위반이다.
- `message`는 서버가 준 한국어 문구를 그대로 싣는다. 같은 문구를 클라에 복제하면 서버와 어긋난다.
- `DETAIL_LIMIT`에 지금 분기를 만들지 않는 이유는 S2에서 발생할 수 없기 때문이다. 못 도는 분기를 미리 넣지 않는다.

### 4-3. 좁히기 상태 기계

```ts
export type NarrowState =
  | { phase: "classifying"; runId: number; raw: string }
  | { phase: "asking"; runId: number; ctx: NarrowCtx; question: Question; picks: Picks }
  | { phase: "advancing"; runId: number; ctx: NarrowCtx }
  | { phase: "retryable"; runId: number; ctx: NarrowCtx; question: Question; error: ApiError }
  | { phase: "done"; ctx: NarrowCtx; reason: DoneReason }
  | { phase: "failed"; error: ApiError };

export type DoneReason = "enough" | "exhausted" | "user_jump" | "malformed";

export interface NarrowCtx {
  sessionId: string;
  classifyOut: Prompt1Out;
  answers: AnswerTurn[];        // { labels: string[] } 또는 { tooHard: true }
  simplify: boolean;
  usedUndo: boolean;
  confidence: number;
}
```

`turnsLeft`는 필드가 아니다(D-4). `turnsLeftOf(ctx, narrowMax)` 파생 함수로 계산한다.

```ts
export type NarrowCmd =
  | { c: "callClassify"; runId: number; input: Prompt1In }
  | { c: "callNext"; runId: number; input: Prompt2In }
  | { c: "abort"; runId: number }                  // D-6
  | { c: "saveSnapshot"; ctx: NarrowCtx }
  | { c: "goRefusal" }
  | { c: "goEntryWithNotice"; notice: "weekly" }
  | { c: "goHandoff"; ctx: NarrowCtx; reason: DoneReason };

export function reduce(s: NarrowState, e: NarrowEvent): [NarrowState, NarrowCmd[]];
```

- `reduce`는 순수 함수다. 네트워크·타이머·난수·현재시각을 쓰지 않는다. `sessionId`와 `runId`는 이벤트로 주입받는다.
- **B-8은 구조로 보장한다.** 응답 이벤트는 `e.runId !== s.runId`면 상태를 바꾸지 않고 명령도 내지 않는다.
- **B-1도 구조로 보장한다.** `phase === "classifying"`에서 `submit`은 전이가 없다.

### 4-4. 종료 판정

```ts
export function decideNext(args: {
  realAnswers: number; out: Prompt2Out | null;
  narrowMin: number; narrowMax: number;
}): { done: true; reason: DoneReason } | { done: false };
```

`out`이 null이거나 형태가 깨졌으면 `{done:true, reason:"malformed"}`. 나머지는 §1-1의 두 조건을 순서대로 본다.

## 5. 검증 (게이트 편입)

새 스크립트 `packages/scripts/e2e-narrow.mjs`를 `gate`에 추가한다. 네트워크 없이 `reduce`·`decideNext`·`turnsLeftOf`만 돌린다.

| 케이스 | 기대 |
|---|---|
| classifying 중 submit | 상태 불변, 명령 0개 (B-1) |
| domain_risk=high | `goRefusal`, 세션 생성 명령 없음 (B-2) |
| classify 형태 깨짐 | `goHandoff`, reason=malformed (B-5) |
| 실답변=narrowMin, enough=true | done, reason=enough |
| 실답변=narrowMax | done, reason=exhausted |
| next 형태 깨짐 | done, reason=malformed (B-7) |
| runId 불일치 응답 | 상태 불변, 명령 0개 (B-8) |
| 어려워요 턴 | 실답변수 불변, 파생 남은턴 불변, simplify=true (D-2) |
| 어려워요 이후 턴 | simplify 유지 |
| 어려워요 3회 연속 | 실답변수 0, 남은턴 = narrowMax (D-2·D-4) |
| simplify=true 상태 | 어려워요 이벤트가 전이 없음 (D-5) |
| 칩 2개 + 직접 입력 | 마지막 턴 labels 길이 3 (B-10) |
| undo 2회 | 두 번째는 무시 (B-11) |
| undo 후 남은턴 | 복구되지 않음 (D-1) |
| 매 턴 | `saveSnapshot` 정확히 1회 (B-13) |
| 402 weekly | `goEntryWithNotice` (B-14) |
| network 실패 | phase=retryable, 화면 이동 명령 없음 (D-7) |
| retryable에서 retry | `callNext` 재발행, 실답변수 불변 (D-7) |
| 세션 전환 | `abort` 명령 발행 (D-6) |
| 임의 ctx | `실답변수 + turnsLeftOf = narrowMax` 항상 성립 (D-4 불변식) |

기존 게이트 무회귀도 완료 조건이다.

## 6. 함께 처리하는 것

- **치수 전환**: `tokens.css` 175~213행(narrow·steps·opt·아키네이터 아바타·thinking·공유 키프레임)을 rem으로 옮긴다.
- **i18n 키**: narrow 문구는 `strings.ts`에 키로 넣고 ko 값만 채운다. 4개 언어는 S5.
- **dev CORS**: local 부트에 dev 전용 CORS 허용(5180 오리진). 프로덕션 오리진 화이트리스트는 SoT §4 `clientCheck` 소관이라 건드리지 않는다.
- **헤더**: S2는 헤더에 도구를 넣지 않는다. 64em 이상 헤더 숨김 규칙은 S4에서 재판단.

## 7. 열린 항목

- **★ free 티어에서 `narrowMin`과 `narrowMax`가 둘 다 3이다.** 그래서 조건 1(`실답변 >= narrowMin && enough`)과 조건 2(`실답변 >= narrowMax`)가 같은 지점에서만 발화하고, **서버가 주는 `enough` 판정이 free에서는 결과를 전혀 바꾸지 못한다.** free는 항상 정확히 3턴이다. 의도인지 확인이 필요하다. `narrowMin`을 2로 낮추면 의도가 일찍 잡힌 사용자가 2턴에 끝낼 수 있다.
- 서버 에러 코드 문자열(WEEKLY_LIMIT 등)의 실제 값은 구현 시 http-app 미들웨어에서 확인해 §4-2를 맞춘다.
- `exhausted` 고지 문구에서 free 대상 상위 티어 안내를 어디까지 할지는 S4 게이팅 UX에서 확정한다.
