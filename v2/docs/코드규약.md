# v2 코드 규약 (사용자 지시 2026-07-20·21 — 첫 단추 규칙)

구현 전 확정하는 하드 규칙. 모든 구현자(opus·위임 에이전트)는 코드 작성 전 이 문서를 정독한다. 위반은 리뷰 반려 사유다.

## 1. 단일 파일 누적 절대 금지
- **파일 = 단일 책임 1개.** 화면 1개, 훅 1개, 리포지토리 1개, 라우트 그룹 1개. "일단 여기 넣자"를 금지한다.
- **크기는 규칙이 아니라 신호다 (사용자 지시 2026-07-28 개정).** 기준은 줄 수가 아니라 단일 책임이다. 200행에서 분리를 검토하고 300행에서 "이 파일이 책임 하나인가"를 반드시 묻되, **답이 예이면 넘겨도 된다.** 구조상 한 파일이 맞는 경우가 있고 억지로 쪼개면 오히려 나빠진다.
  - 넘기는 파일은 게이트의 `ALLOWLIST`에 사유와 함께 등록한다. 게이트는 초과를 실패로 만들지 않고 **미등록 초과만** 잡는다. 예외를 없애는 것이 아니라 보이게 하는 것이 목적이다.
  - 실측 사례: `tokens.css` 564행은 "v1 디자인 시스템 정본" 하나라서 단일 책임이 맞다. 등록 대상이지 분할 대상이 아니다. 반면 v1 `App.tsx` 904행은 화면 10종과 상태 50필드를 한 파일에 쌓은 것이라 책임이 여럿이었다.
- 문서도 동일: 진행 이력을 한 문서에 append하지 않는다. 상태 문서는 "현재 상태"만 유지하고, 이력은 git이 담당한다.

## 2. 인덱싱 철저
- 각 패키지는 루트에 **역할·구조를 설명하는 짧은 README**(10~20행)와 공개 표면을 정의하는 **index.ts(배럴)**를 갖는다. 패키지 밖에서는 배럴 경유로만 import(딥 임포트 금지 — dependency-cruiser로 강제).
- `v2/docs/`는 `_index.md`가 문서 카탈로그의 정본이다. 문서 추가·폐기 시 _index 갱신이 커밋 조건.
- 새 화면·모듈을 추가하면 해당 패키지 README의 구조 맵을 같은 커밋에서 갱신한다.

## 3. 소프트웨어 공학 패턴 (강제 지점)
| 패턴 | 적용 지점 | 근거 |
|---|---|---|
| 포트-어댑터(헥사고날) | 모든 외부 자원(LLM·검색·DB·캐시·플랫폼 API) — 포트는 shared, 구현은 adapters | SoT §0-1, 3계층 실행의 전제 |
| 의존성 주입 | core·http-app은 포트 구현을 생성하지 않고 부트에서 주입받는다 | 테스트 가능성, 계층 교체 |
| 리듀서(상태 기계) | ui-shared 화면 상태 — 액션 타입 명시, 화면별 리듀서 분리(단일 거대 리듀서 금지) | v1 useReducer 승계 + 누적 금지 |
| 리포지토리 | 영속 접근(Session/Asset/Knowledge/Project/UserRepository) — SQL은 리포 구현 밖으로 새지 않는다 | SoT §3-3 |
| 팩토리(부트 조립) | adapters/{aws,local}의 부트 = 포트 구현 조립 팩토리 하나로 집중 | 계층 분기의 유일 허용 지점 |
| 전략 | 모델 라우팅(위험도별)·프라이머 템플릿(로케일별) 등 분기 로직 | if-else 누적 방지 |
- 패턴을 위한 패턴은 금지: 위 표 밖에서는 "이 분기가 셋째로 늘었나?"가 패턴 도입 신호다.

## 4. 작성 스타일
- 주석은 코드가 못 보여주는 제약만(전역 규칙: 특수기호 금지, 사람이 쓰는 문장으로).
- 네이밍·구조는 기존 파일의 관례를 먼저 읽고 계승한다(스타일 분석 후 작성).
- 에러는 단계별로 잡아 어느 단계가 왜 실패했는지 남긴다(자동화 강건성 규칙 준용).

## 5. 게이트 연결
- C1 완료 기준에 본 규약 위반 0을 포함한다: 경계 게이트 3종 + 파일 크기 검사(스크립트) + 배럴 경유 import 검사.
- 위임 에이전트 프롬프트에는 이 문서 경로를 필수로 첨부한다.

# 적층형 방지 규칙 (사용자 지시 2026-07-28, 전역 승격)

> 배경: 버그 수정과 테스트를 반복해서 나온 산출물은 결국 땜질 스파게티가 된다. 패치는 자기가 무엇을 깨뜨렸는지 모르기 때문이다. 앞선 결정이 코드 안에 암묵적으로만 있으면 나중 패치가 그것을 조용히 뒤집고도 테스트를 통과한다.
> 실측 근거: v1은 판단 자체는 옳았고 근거 주석도 좋았다(`theme.css:451-456`의 폭 오버라이드 사유, "어려워요는 답이 아니라 난이도 신호"). 문제는 그 결정들이 코드 주석에 흩어져 **아무도 전체를 열거할 수 없었다**는 점이다. 그래서 v2 S1이 v1이 풀어 둔 폭 상한을 다시 씌웠고, "어려워요" 이중 카운터 버그가 몇 달을 살아남았다.

## 6. 동작 규칙은 ID·출처·근거·테스트를 갖는다

구현 전 스펙에 동작 규칙을 표로 명시한다. 각 규칙은 넷을 모두 갖춰야 한다.

| 요소 | 없으면 생기는 일 |
|---|---|
| **ID** (B-1, D-2 등) | 나중 패치가 무엇을 깨는지 지목할 수 없다 |
| **출처** (파일:행 또는 사용자 확정 일자) | 어디서 온 결정인지 몰라 재조사를 반복한다 |
| **근거** (왜 이렇게 하는가) | 미래에 "개선"이라며 되돌리고 같은 문제를 재발시킨다 |
| **테스트** (검증 케이스 이름) | 규칙이 살아 있는지 확인할 방법이 없다 |

근거가 특히 중요하다. 예: "되돌리기는 첫 질문으로 회귀한다"에 "한 단계씩 뒤로 가면 매번 API가 재호출되어 왕복 비용이 통제 불능"이라는 근거가 붙어야, 나중에 누가 한 단계 되돌리기로 바꾸지 않는다.

## 7. 버그가 나오면 고치기 전에 분류부터 한다

| 분류 | 조치 |
|---|---|
| 구현이 규칙을 어겼다 | 코드 수정 + 그 규칙의 테스트 추가 |
| 규칙이 틀렸다 | **스펙을 먼저 개정**하고 구현 |
| 규칙이 없었다 | **규칙을 먼저 신설**하고 구현 |

**"그냥 고친다"는 선택지에 없다.** 이 분류를 건너뛰면 결정이 코드에만 쌓이고, 그것이 곧 적층형이다.

## 8. 막을 수 있으면 검사하지 않는다

잘못된 상태를 허용해 놓고 검사로 막으면, 검사를 빠뜨린 경로마다 버그가 난다. 애초에 표현 불가능하게 만드는 쪽이 위다.

- 나쁨: 카운터 둘을 두고 둘이 일치하는지 테스트한다
- 좋음: 카운터를 하나만 두고 나머지는 파생한다 (저장하지 않으면 어긋날 수 없다)

실측 사례: v1의 "어려워요" 버그는 예산과 답변 수를 따로 저장했기 때문에 생겼다. 하나로 합치자 버그가 재발 불가능해지고 종료 조건도 셋에서 둘로 줄었다.

## 9. 코드를 크게 고치기 전에 스펙이 먼저다

한 서브시스템을 실질적으로 바꾸는 작업은 스펙(동작 규칙 표 + 계약 + 검증 표)을 먼저 내고 검토를 받은 뒤 구현한다. 실측 사례: S1 치수 작업을 스펙 없이 51곳 고쳐서 방향 자체가 틀렸고 전부 되돌렸다. 같은 작업을 S2에서 스펙 먼저로 하자 v1에 몇 달 살아 있던 버그 두 개가 코드 한 줄 쓰기 전에 나왔다.
