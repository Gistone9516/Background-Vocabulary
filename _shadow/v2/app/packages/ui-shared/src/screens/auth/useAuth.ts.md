## 판단 1 — 플랫폼 차이는 AuthFlow 포트로만 들어온다 (C4 S2)

**결정.** `redirectUri: string` 옵션이 `flow: AuthFlow | null`로 바뀌었다:
`{ platform, redirectUri(), navigate(), waitForCallback?() }`. PKCE 생성·state 검증(A-4)·교환·토큰
저장은 이 훅이 갖고, **"어떻게 브라우저로 가고 어떻게 돌아오는가"만** 셸이 정한다.

**왜 이 모양인가.** 웹과 데스크톱의 로그인은 이동 방식만 다르다 — 웹은 페이지가 떠났다 돌아오고
(`location.assign` + 마운트 경로), 데스크톱은 같은 페이지에서 루프백 콜백을 기다린다
(`waitForCallback`). 검증·교환이 같으므로 거기서 가르면 한쪽만 위조에 열린다. 그래서
`completeExchange`를 공통 반쪽으로 뽑아 **두 경로가 같은 state 검증을 탄다** `[코드]`.

journey의 그림자 노트가 낡는 조건으로 미리 적어 둔 그대로다: "redirectUri 외의 것이 필요해지면
**포트를 넓힐 것** — 여정에 플랫폼 분기를 넣는 순간 판단 1이 무효가 된다." 그 조건이 S2에서
발동했고, 예고된 방향으로 풀었다.

**뒤집으면 깨지는 것.** "데스크톱 로그인은 어차피 다르니 desktop 전용 훅을 만들자"가 자연스러운
되돌림이다. 그러면 state 검증·401 재발급·실패 문구가 두 벌이 되고, 한쪽만 고친 수정이 계속
생긴다 — D-12가 막는 정확히 그 상태다.

## 판단 2 — 마운트 콜백 경로는 남는다. 데스크톱에서 자연 무동작이다

웹의 마운트 경로(`location.search`의 code 감지)는 그대로다. 데스크톱은 웹뷰가 이동하지 않으므로
search에 code가 실릴 일이 없고 이 effect는 조건에서 걸러진다 — **분기를 추가하지 않고 무동작이
성립하는** 배치다. `history.replaceState`(코드 재사용 방지)도 웹 경로에만 있다.

## 판단 3 — available = clientId ∧ flow

능력(flow)과 등록(clientId) 어느 쪽이 없어도 버튼이 뜨지 않는다(A-2와 같은 강등 경로).
S1의 "auth: null → clientId 죽이기" 우회가 사라지고 훅이 직접 판정한다.

**실측** `[실행]`: mock 서버(clientId 없음)에서 웹·데스크톱 둘 다 버튼 없음 확인(창 캡처).
데스크톱 루프백 흐름의 실 왕복은 **Google 콘솔 등록(사용자) 후**가 마감이다(DS2-9) — 코드 경로는
컴파일·게이트로만 확인된 상태다. `[미검증]` 표시를 남긴다.

## 그때 무엇을 근거로 삼았나 — 자기 신고

- **읽은 것** — 이 파일 전문(개정 전), pkce.ts 함수 표면(브리핑), AuthButton available 사용처.
- **브리핑** — S2 현장 렌즈가 마운트 처리·scratch 키·signIn 단계를 행 번호로 보고했다.
- **실행 확인** — tsc 3면, 게이트 241 PASS. 데스크톱 실 로그인 왕복은 미실측(위).
- **위치** — C4 S2 커밋.

## 이 노트가 낡는 조건

- **Google 콘솔 등록 후 실 로그인 실측**이 되면 판단 3의 `[미검증]`이 지워진다. 안 되면 —
  특히 루프백 redirect_uri의 포트 가변성이 콘솔 등록과 충돌하면 — `redirectUri()` 계약을 다시 본다.
- **AuthFlow에 세 번째 플랫폼**(모바일 등)이 오면 waitForCallback의 의미(같은 페이지 유지)가
  유지되는지 먼저 확인할 것.
- **refresh 응답에 user가 실리게 되면** AuthSession의 "refresh에는 user가 없다" 주석과 함께
  locale 동기화 시점(journey)도 다시 본다.
