# EditSheet.tsx — FAB 트리거가 왜 폭이 아니라 가시성인가

작성 2026-08-03 (C5-S2 T-5). 대상 = `v2/app/packages/ui-shared/src/screens/primer/EditSheet.tsx` + `styles/primer.css`.

## 두 질문을 갈랐다

FAB(좌하단 원형 편집 버튼)에는 서로 다른 질문이 둘 있고, 둘을 한 조건으로 답하려다 처음에 꼬였다.

| 질문 | 답 | 판정 주체 |
|---|---|---|
| 이 화면에 FAB이 **있어야 하나** | 좁은 화면에만. 넓은 화면은 우측 열이 이미 편집 진입점이다 | **CSS** (`@media (min-width: 64em)`에서 `display:none`) |
| 지금 FAB을 **띄워야 하나** | '이대로 복사'가 눈에 보일 때. 끄트머리라도 보이면 | **JS** (`IntersectionObserver`, `threshold: 0`) |

## 왜 폭으로 통일하지 않았나

"폭이 X 미만이면 FAB"은 쓰기 쉽고 틀린다. 사용자가 FAB을 원하는 순간은 화면이 좁을 때가 아니라 **편집할 대상이 눈앞에 있을 때**다. 종착 화면 맨 위 안내문을 읽는 중에 편집 버튼이 떠 있으면, 아직 무엇을 편집할지도 모르는 상태에서 선택을 요구하는 꼴이다 — 이 제품이 없애려는 바로 그 비용이다(표현 비용 면제).

그래서 트리거를 **복사 CTA의 가시성**으로 잡았다. 그 버튼이 보인다는 것은 사용자가 "이제 이걸 가져갈까" 지점에 도달했다는 뜻이고, 편집 의사가 생기는 자리와 정확히 겹친다.

## 왜 JS가 폭을 재지 않나

반대 방향의 유혹은 `window.innerWidth`를 읽어 JS가 둘 다 판정하는 것이다. 버렸다. 폭 판정이 JS로 올라오면 CSS와 JS가 같은 임계값을 **두 벌** 갖게 되고, 하나를 고칠 때 다른 하나가 남는다 — 화면 폭 하나에 진실이 둘이 되는, `selection.ts`에서 막은 것과 같은 형태의 문제다.

배치는 CSS가 전담한다. `.editFab { display: none }`은 미디어 쿼리 한 줄이고, JS는 그 존재 여부를 알 필요가 없다. 넓은 화면에서 관찰자가 계속 돌아도 결과가 화면에 안 나타날 뿐 해가 없다.

## 관찰자가 없을 때

`IntersectionObserver`가 없는 환경에서는 **항상 보이는 쪽으로** 떨어진다. 편집 진입점이 사라지는 것보다 불필요하게 떠 있는 편이 낫다 — 앞은 기능 상실이고 뒤는 거슬림이다.

## 검증되지 않은 부분 (남아 있음)

**이 규칙은 기계 검증이 없다.** 가시성도 제스처도 브라우저 안에서만 판정된다. `e2e-primer.mjs`는 `selection.ts`의 순수 함수만 본다. 좁은 화면 실측은 사용자 눈으로 마감해야 하고, 2026-08-03 시점에 아직 안 했다.
