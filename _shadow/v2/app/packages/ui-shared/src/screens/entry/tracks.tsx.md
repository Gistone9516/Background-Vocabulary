## 판단 1 — 트랙은 `.hero` 안, `.heroGlow` 의 형제다. 다른 자리가 없다

**결정.** 붙일 자리 후보가 셋이었고 둘이 배제되어 하나만 남았다.

| 자리 | 결과 |
|---|---|
| `.heroGlow` **안**(칩의 형제) | 배제 — `.aurora{bottom:0}` 이 `.heroGlow` 바닥 기준이고 그 바닥은 지금 `.suggest` 가 정한다. 안에 넣으면 오로라가 트랙까지 덮는다 `[코드]` |
| `.hero` **안**, `.heroGlow` 형제 | **채택** |
| `.entryMain` 안, `.hero` 형제 | 배제 — `.hero{flex:1}` 이 남는 세로를 먼저 먹어 트랙이 접힘선 아래로 밀린다 `[코드]` |

**왜 가운데가 되는가** `[코드]`. `.hero` 는 flex 세로 컨테이너이고 `.entryMain .hero` 가
`justify-content: flex-start` 로 덮는다. 그래서 `.heroGlow` 다음 flex 항목으로 두면 칩 바로
아래에 붙고 남는 공간이 트랙 **뒤로** 모인다.

**뒤집으면 깨지는 것.** "칩 바로 옆이 자연스럽다"며 `.heroGlow` 안으로 옮기면 오로라가 카드를
덮어 카드의 테두리·그림자가 배경과 싸운다. 반대로 "hero 밖이 구조적으로 깔끔하다"며 `.hero` 의
형제로 올리면 넓은 뷰포트에서 트랙이 화면 밖으로 내려간다 — 재인이 목적인 카드에는 기능 상실이다.
둘 다 컴파일되고 게이트도 통과한다.

## 판단 2 — DOM 은 하나이고 넓은 화면 지그재그를 받아들였다

**결정.** DOM 순서는 카드 → 가변 → 마인드맵. 좁은 화면의 시각 순서와 일치하고, 넓은 화면에서는
격자가 마인드맵을 왼쪽 아래로 올린다. 그 결과 넓은 화면에서 Tab 이 왼쪽 위 → 오른쪽 → 왼쪽 아래로
움직인다. **사용자 확정** `[대화]` 2026-08-18 — "넓은 화면은 카드, 마인드맵, 가변" 배치를 지정한 뒤,
분리 DOM 이 가능한지 물었고 불가 사유를 듣고 "지그재그 진행"으로 정했다.

**왜 DOM 이 하나인가** `[코드]`. 두 벌 렌더는 D-12 가 막는다(`SourcePanel.tsx` 주석: "두 벌로
만들면 한쪽만 고쳐져 갈라지고 컴파일은 계속 된다"). JS 폭 측정은 `EditSheet.tsx` 주석이 막는다
("그 판정은 CSS 가 한다. JS 로 폭을 재면 같은 규칙이 두 곳에 생긴다"). 남는 것은 격자 재배치뿐이고,
DOM 이 하나이므로 두 화면 중 한쪽은 반드시 어긋난다.

**대가를 상쇄하는 것이 V-6 이다.** 세 블록이 순서에 기대지 않고 각자 자기 라벨을 갖는다.
어느 순서로 만나든 그 자체로 이해되면 순서 차이가 의미를 바꾸지 않는다.

**뒤집으면 깨지는 것.** "좁은 화면 쪽을 DOM 으로 두는 게 접근성에 낫다"는 판단은 **한 번 내렸다가
철회한 것이다.** 겪는 사람 수가 다르다 — 좁은 화면은 대부분 터치라 Tab 을 안 쓰고 스크린리더
사용자는 화면을 안 보므로 어긋남 자체가 없다. 넓은 화면 지그재그는 데스크톱 키보드 사용자가
매번 겪는다. 되돌리려는 세션은 이 비대칭을 먼저 볼 것.

## 판단 3 — 마인드맵 칸은 비어도 자리를 지킨다

**결정.** `.etMap:empty { min-height: 5.5rem }`. `mapPanel` 의 기존 관례("null 이면 절 자체가
안 뜬다")와 **다른 선택**이다. 사용자 확정 `[대화]` 2026-08-18("남겨").

**왜 다른가.** `PrimerScreen` 의 `mapPanel` 은 세로로 흐르는 패널의 한 절이라 비면 그냥 사라지고
위아래가 붙는다. 여기는 격자 칸이라 비면 **왼쪽 열의 행 구성이 바뀐다** — 카드가 왼쪽 전체로
넓어졌다가 S4 가 채우면 반으로 줄어들어 같은 화면이 두 번 바뀐다.

**5.5rem 은 잠정값이고 실측으로 정한 것이 아니다** `[미검증]`. S4 가 넣을 소형 창의 크기를 모른다.

**셋 다 null 이면 컨테이너를 안 그린다** `[코드]`. 신규 사용자에게 설명 없는 빈 격자가 보이는 것을
막는다. 마인드맵만 비는 것과 다른 경우다.

## 실행으로 확인한 것 `[실행]`

목업(실제 `bundle.css` + 실제 DOM 구조)을 chromium 헤드리스로 1280x860 과 390x844 에서 렌더했다.
재현 명령은 리포에 없다 — 스크래치패드에서 만든 일회성 하네스였다. **그래서 이 항목은 다음 세션이
재현할 수 없다.** 결과만 적는다.

- 넓은 화면: 카드가 왼쪽 열, 오른쪽은 가변 슬롯 자리로 빔. 오로라가 카드 위에서 끝남 — 판단 1 확인
- 좁은 화면: 카드가 첫 화면 안에 완전히 들어옴. 판단 1 의 세 번째 후보를 배제한 이유(접힘선 아래로
  밀림)가 채택안에서는 발생하지 않음을 확인
- 빈 마인드맵 칸은 여백으로만 읽힘 — 판단 3 의 `[미검증]` 이 그대로 남는다

## 그때 무엇을 근거로 삼았나 — 자기 신고, `[미검증]`

- **읽은 것** — `EntryScreen.tsx` 전문, `shell.css`·`tokens.css` 의 진입 화면 관련 규칙 전량,
  `PrimerScreen`/`SourcePanel` 의 슬롯 배선.
- **안 읽은 것** — `terms`·`narrow` 화면의 CSS. 이 슬라이스가 안 건드린다.
- **브리핑** — **이 슬라이스에서는 브리핑 쌍을 돌리지 않았다.** 대신 하루 전 S3a 에서 12대(탐색 6 +
  비판 6)가 같은 파일들을 실측·대조했고 그 결과가 `UIUX-인덱스.md` 로 커밋돼 있다. 브리핑보다 깊다.
  **판단 1 의 후보 셋과 배제 사유는 전부 그 인덱스 §4-7 에서 나왔다** — 인덱스가 없었으면 세 후보를
  구분조차 못 했다.
- **알고도 미룬 것** — 5.5rem 실측, 빈 칸 표시 방식.
- **위치** — C5-S3 구현, 게이트 통과 직후.

## 이 노트가 낡는 조건

- **S4 가 마인드맵을 꽂으면** 판단 3 의 `min-height` 는 실측값으로 바뀌어야 한다. 그때 이 문단을
  지우지 말고 등급을 올릴 것.
- **가변 슬롯에 내용이 들어오면** 넓은 화면 오른쪽 열이 처음으로 차고, 판단 1 의 "오른쪽이 빔"이라는
  실측 서술이 낡는다.
- **`.hero` 나 `.heroGlow` 의 flex 구성이 바뀌면** 판단 1 의 배제 논거 둘이 동시에 흔들린다.
  그때는 세 후보를 다시 대볼 것.
