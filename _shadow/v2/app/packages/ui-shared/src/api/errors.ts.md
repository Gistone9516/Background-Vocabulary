# api/errors.ts — 판단 기록

**정본** = `v2/app/packages/ui-shared/src/api/errors.ts`. 경로는 리포 루트 기준, 명령은 `v2/app`에서.
규칙 원문(`S-*`) → `v2/docs/specs/C3-S5-세션과프로젝트.md`.

등급: `[실행]` 실행 출력 / `[코드]` 코드를 읽었음 / `[대화]` 인용 가능한 사용자 발언 / `[문서]` 문서 하나 / `[미검증]`.

## 판단 1 — 서버가 보낸 `message`를 화면에 띄우지 않는다 (S-35)

**결정.** `ERROR_KEY`로 `kind`를 문구 키에 대응시키고, 화면은 그 키로 자기 표에서 꺼낸다.
서버 `message`는 필드에 남지만 화면에 가지 않는다. 확립 커밋 = 이 노트와 같은 커밋.

**이 판단은 이 파일의 기존 결정을 뒤집는다.** 파일 위쪽 주석이 정반대를 말하고 있었다 `[코드]`:
> 서버 문구를 그대로 싣는다. 같은 문구를 클라에 복제해 두면 서버가 바뀔 때 조용히 어긋난다.

그 우려는 유효하다. 뒤집은 근거는 **코드는 열거 가능하고 문구는 그렇지 않다**는 것이다 —
코드로 맞추면 서버가 문구를 바꿔도 어긋날 것이 없고, 문구로 맞추면 서버가 문구를 바꿀 때마다
어긋난다. 그리고 서버는 로케일을 모른다 `[코드]`(`gating.ts`·`auth-routes.ts`의 13건이 한국어
고정) — 그대로 띄우면 영어 화면에 한국어 오류가 뜬다.

**뒤집으면 깨지는 것.** 되돌리는 자연스러운 이유는 위 주석 그대로다("문구 이중화를 피한다").
되돌리면 **로케일이 있는 화면에 로케일이 없는 문구가 다시 들어온다.** 그 상태는 ko 사용자에게는
정상으로 보이고, 테스트도 ko로 도니 잡히지 않는다. 되돌리려면 먼저 서버가 요청의
`outputLocale`을 읽어 문구를 골라야 하고, 그건 서버에 문구 표를 두는 것이므로 정본이 둘이 된다.

**`not_restorable`을 새 종류로 가른 이유.** `NOT_RESTORABLE`이 `not_found`와 같은 `kind`로
묶여 있었는데 문구는 달랐다 `[코드]`("되돌릴 수 있는 기간이 지났어요" vs "찾을 수 없어요").
**하나의 종류가 두 문구를 가지면 코드에서 키를 정할 수 없다.** 종류를 갈라 각자 키를 갖게 했다.

**타입이 막는다는 것을 실행으로 확인했다** `[실행]`. `kind`를 하나 더하고 `ERROR_KEY`에 넣지
않은 채 `npx tsc -b`를 돌려 이 오류를 받았다:
> `error TS2741: Property 'quota_gone' is missing in type ... but required in type 'Record<...>'`
통과만 확인하면 막는지 알 수 없으므로 이 단계는 생략 가능한 것이 아니다.

**곁가지로 지운 것.** 화면 세 곳에 `(state.error as { message?: string }).message ?? tr("err_network")`
가 복제돼 있었다 `[코드]`. 캐스트로 유니온을 뚫고 문구를 꺼내는 코드였고, 세 곳이 각자 조금씩
다르게 진화할 수 있는 상태였다. `errorKey` 하나로 접었다.

**그때 무엇을 근거로 삼았나** — 자기 신고, `[미검증]`.
- **읽은 것** — `errors.ts` 전문, 화면 4곳의 렌더 지점, `primer.ts` 전문.
- **안 읽은 것** — `gating.ts`·`auth-routes.ts` 본문. 13건이라는 수와 한국어 고정이라는 사실은
  주변 렌즈의 보고를 그대로 받았다. 개수를 직접 세지 않았다.
- **브리핑** — ②-b 착수 시 돌렸고, 서버 문구 13건이 사각지대라는 것을 그때 받았다.
  내 원래 계획에는 이 항목이 없었다.
- **알고도 미룬 것** — 서버가 로케일별 문구를 갖는 안. 계약 변경이라 열린 항목으로 남겼다.
- **위치** — ②-b 이후, S-31과 같은 커밋.

## 판단 2 — `CAPACITY`를 `rate_limited`에서 갈랐다 (판단 1의 조건이 발동한 사례)

**결정.** `CAPACITY`가 `kind: "capacity"`를 갖고 `err_capacity` 키를 쓴다.
확립 = C5-S1 커밋. 규칙 원문 = 같은 스펙 E-13.

**왜.** 두 오류는 사용자에게 다른 말을 해야 한다 — `RATE_LIMITED`는 "당신이 빨리 썼다"(기다리면
풀림), `CAPACITY`는 "우리 쪽이 혼잡하다"(우리 잘못이고, 기다려도 안 풀릴 수 있다). 같은
`kind`로 접혀 있어 **사용자가 우리 장애를 자기 잘못으로 읽는 상태**였다 `[코드]`.

**이 노트가 그 상태를 예고하고 있었다.** 아래 "낡는 조건"의 두 번째 항목이 정확히 이 경우다 —
"키를 만들기 싫어서 기존 키를 재사용하려는 순간, 두 오류가 같은 말을 하게 되는지 먼저 볼 것."
발동했고, 갈랐다.

**뒤집으면 깨지는 것.** "둘 다 429고 둘 다 기다리면 되니 하나면 충분하다"가 되돌리는 이유가
된다. 되돌리면 전역 캡이 걸린 순간 — 즉 **서비스가 멈춘 순간** — 전 사용자가 "잠시 후 다시
시도해 주세요"를 보고 자기 사용량 탓으로 이해한다. 우리는 그 사이 아무 알림도 못 받는다
(전역 캡 계측은 아직 없다, `limits.ts.md` 판단 2).

**번역은 `port-i18n.mjs`의 `AUTHORED`에 넣었다** `[실행]`. 생성기가 빈 칸을 스스로 보고해
(`문구를 못 찾은 키 1건 — AUTHORED에 넣거나 …`) 손편집을 막았다. 그 경로를 따르면 `[AI]`
표기가 자동으로 붙어 이식분/작성분 구별이 유지된다(`strings.ts.md` 판단 3-b).

## 이 노트가 낡는 조건

- **서버가 `outputLocale`을 읽어 문구를 고르게 되면** 이 판단의 근거가 사라진다. 그때는 정본이
  서버로 옮겨가고 `ERROR_KEY`는 폴백이 된다 — 그 상태를 원하는지 먼저 정할 것.
- **`kind`를 추가하면** 타입이 키를 요구한다. 그것이 의도다. 키를 만들기 싫어서 기존 키를
  재사용하려는 순간, 두 오류가 같은 말을 하게 되는지 먼저 볼 것.
- **`ERROR_KEY`가 `Record`가 아닌 형태로 바뀌면**(인덱스 시그니처, `Partial`) 위 실행 확인이
  무의미해진다. 그 형태로 바꿀 때는 음성 검사를 다시 돌릴 것.
