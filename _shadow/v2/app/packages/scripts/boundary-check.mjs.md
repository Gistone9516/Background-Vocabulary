## 판단 1 — 자산 방향은 패키지 이름이 아니라 **진입점 경로**로 판정한다

**결정.** `ASSET_ALLOWED`의 값이 `"ui-shared"`(패키지)에서 `"ui-shared/vars.css"`(진입점)로 바뀌었고,
비교 대상도 `target`에서 `rest`(패키지/서브패스 전체)로 바뀌었다.

```
landing: new Set(["ui-shared/vars.css"])    // 변수만
web:     new Set(["ui-shared/styles.css"])  // 앱 스타일 진입점 전체
```

**계기.** 패키지 단위로 두었을 때 게이트가 **규칙보다 넓었다.** L-2가 말한 것은 "디자인 토큰 CSS만"인데
게이트는 `ui-shared`의 어떤 `.css`든 통과시켰고, 그래서 랜딩이 `styles.css`를 가져온 상태를 통과로
판정했다. 그 상태의 실제 결과는 실측으로 확인했다 `[실행]`: `main`이 내부 스크롤 판이 되어 두 절이
화면에서 사라진 것처럼 보였고, **여섯 절 전부 렌더는 되어 있었다.** 화면이 "깨진 것"이 아니라
"콘텐츠가 적은 것"처럼 보이므로 사람이 통과로 착각한다.

**규칙보다 넓은 게이트는 게이트가 아니다** — 통과가 규칙 준수를 뜻하지 않게 되기 때문이다.

**음성 확인을 했다** `[실행]`. 랜딩의 import를 `styles.css`로 바꾸고 돌려서 이 출력을 받았다:
> `허용밖 자산 의존: landing → ui-shared/styles.css (@vock/ui-shared/styles.css)` — 총 1건, exit=1

같은 라운드에서 되돌린 뒤 통과(exit=0)도 확인했다. **통과만 보면 막는지 알 수 없다.**

**이 검사의 한계를 알고 둔다.** 이 게이트는 **import 문자열만** 본다 — 그 이름이 실제로 어떤 파일로
해석되는지는 보지 않는다. 그래서 "진입점 이름과 파일 이름을 같게 둔다"가 이 게이트가 뜻을 갖는
전제이고, 그 전제를 `ui-shared/package.json`이 지킨다. 처음에 변수 진입점을 `./tokens.css`로 냈다가
같은 폴더의 다른 `tokens.css`와 이름이 겹쳐 이 전제가 깨졌고, 이름을 `vars.css`로 고쳤다
(→ `_shadow/v2/app/packages/ui-shared/src/styles/vars.css.md` 판단 2).

**뒤집으면 깨지는 것.** 되돌리는 자연스러운 이유는 "CSS 파일을 하나 추가할 때마다 이 맵을 손봐야 해서
번거롭다"다. 넓히면 위 결함이 통과 상태로 돌아온다. 자산을 하나 더 내보낼 일이 생기면 **맵에 한 줄을
더하는 것이 맞다** — 그 한 줄이 "누가 누구의 어떤 자산을 쓰는가"의 유일한 기록이다.

## 판단 2 — `isAssetEntry`는 딥임포트 검사만 면제하고 방향 판정은 면제하지 않는다

**결정(이전 라운드에서 확립, 여기 기록).** 자산 진입점은 배럴 규칙(딥임포트 금지)에서만 예외이고,
방향은 `ASSET_ALLOWED`로 반드시 판정한다. 순환 그래프에는 넣지 않는다 — CSS import는 실행 순서를
만들지 않는다.

처음에는 "자산이면 검사를 건너뛴다"로 두려 했다. 그러면 **누가 누구의 자산을 쓰는지가 아무 데도
적히지 않는다.** 그리고 그 수정이 이미 통과하던 `web`을 깨뜨렸다 `[실행]` — `web/main.tsx`도 같은
진입점을 쓰는데 `ASSET_ALLOWED`에 `web` 항을 빠뜨렸기 때문이다. **새 검사를 넣을 때 기존 통과 경로를
함께 시험해야 한다**는 실측이 여기서 나왔다.

## 그때 무엇을 근거로 삼았나 — 자기 신고, `[미검증]`

- **읽은 것** — 이 파일 전문, `ui-shared/package.json` exports 전문, 랜딩 `index.astro` 전문.
- **안 읽은 것** — `relation-index.py`의 CSS 파싱 경로. `vars.css`를 새로 보게 되는지는 브리핑 보고를
  받았고(`:root`는 pseudo-class로 걸러져 미사용 클래스로 안 잡힘) 직접 확인하지 않았다.
- **브리핑** — 현장·주변 두 대. 현장이 이 게이트가 "문자열만 본다"는 성질과 이름 충돌을 잡았다.
- **주변 보고를 재측정해 뒤집은 것** — "`PROMPT_ROOTS`가 아직 2개 등록"이라는 보고. 실제 3개다
  `[실행]`(`portability-guard.mjs:18`).
- **알고도 미룬 것** — `package.json`의 `exports`와 이 파일의 `ASSET_ALLOWED`가 **손으로 맞춰야 하는
  두 개의 소스**라는 것. exports를 읽어 자동으로 대조하면 없앨 수 있으나 이번 슬라이스의 일이 아니다.
  아래 "낡는 조건"에 남긴다.
- **위치** — S6, 랜딩 CSS 격리 수정과 같은 커밋.

## 이 노트가 낡는 조건

- **`ui-shared`가 자산 진입점을 추가·개명하면** 이 파일과 `package.json`이 함께 움직여야 한다.
  둘을 대조하는 검사는 없다 — 어긋나면 게이트가 조용히 통과하거나 조용히 막는다.
- ~~`desktop` 패키지가 생기면 키가 필요하다~~ → **발동·해소 2회(C4 S1·S2).** S1에서 `desktop`
  키(코드·자산 둘 다), S2에서 `tauri` 키(`ALLOWED`만 — 자산 없음)와 `desktop → tauri` 방향이
  들어갔다. 두 번 다 패키지 신설과 같은 커밋이다.
- **이 게이트가 exports 맵을 읽어 자동 대조하게 되면** 판단 1의 "문자열만 본다"는 한계가 사라지고,
  그때는 진입점 이름과 파일 이름을 같게 두는 규약이 필요 없어진다.
